## Flutter 布局规则

约束向下传递。尺寸向上报告。父级设置位置。

具体流程：

* 一个小部件从其父级获取自己的约束。约束只是一组 4 个双精度浮点数：最小和最大宽度，以及最小和最大高度。
* 然后，小部件遍历自己的子级列表。小部件逐一告诉其子级它们的约束是什么（每个子级可能不同），然后询问每个子级它想要成为什么尺寸。
* 然后，小部件逐一地定位其子级（水平在x轴上，垂直在y轴上）。
* 最后，小部件将其自身的尺寸（当然，在原始约束范围内）告知其父级。

协商过程大致如下：

**小部件**：“嘿，父级，我的约束是什么？”
父级：“你必须是0到300像素宽，0到85像素高。”
**小部件**：“嗯，因为我想要有5像素的填充，所以我的子级最多可以有290像素的宽度和75像素的高度。”
**小部件**：“嘿，第一个子级，你必须是0到290像素宽，0到75像素高。”
**第一个子级**：“好的，那我希望是290像素宽，20像素高。”
**小部件**：“嗯，因为我想把我的第二个子级放在第一个子级下面，所以我的第二个子级只有55像素的高度了。”
**小部件**：“嘿，第二个子级，你必须是0到290像素宽，0到55像素高。”
第二个子级：“好的，我希望是140像素宽，30像素高。”
**小部件**：“很好。我的第一个子级的位置是x: 5和y: 5，我的第二个子级的位置是x: 80和y: 25。”
**小部件**：“嘿，父级，我决定我的尺寸将是300像素宽，60像素高。”

## 局限性

Flutter 的布局引擎被设计为一次性过程。这意味着 Flutter 布局其小部件的效率非常高，但也导致了一些局限性：

* 一个小部件只能在其父级给出的约束范围内决定自己的尺寸。这意味着一个小部件通常不能拥有它想要的任何尺寸。
* 一个小部件不能知道也无法决定自己在屏幕上的位置，因为是小部件的父级决定了小部件的位置。
* 由于父级的尺寸和位置反过来也取决于它自己的父级，因此不考虑整个树就不可能精确定义任何小部件的尺寸和位置。
* 如果子级想要与父级不同的尺寸，而父级没有足够的信息来对齐它，那么子级的尺寸可能会被忽略。在定义对齐方式时要具体。

在 Flutter 中，小部件由其底层的 RenderBox 对象渲染。Flutter 中的许多盒子，特别是那些只接受一个子级的盒子，将其约束传递给它们的子级。

通常，根据它们如何处理约束，有三种类型的盒子：

* 那些试图尽可能大的盒子。例如，Center 和 ListView 使用的盒子。
* 那些试图与子级尺寸相同的盒子。例如，Transform 和 Opacity 使用的盒子。
* 那些试图成为特定尺寸的盒子。例如，Image 和 Text 使用的盒子。

有些小部件，例如 Container，根据其构造函数参数的不同而类型各异。Container 构造函数默认情况下会尝试尽可能大，但如果你给它一个width，例如，它会尝试遵循该宽度并成为那个特定尺寸。

## 紧密约束与松散约束

### 紧密约束

紧密约束只提供一种可能性，即一个精确的尺寸。换句话说，紧密约束的最小宽度等于最大宽度；并且最小高度等于最大高度。

### 松散约束

松散约束的最小值为零，最大值为非零。

有些盒子会放松传入的约束，这意味着最大值保持不变但最小值被移除，因此小部件的最小宽度和高度都可以等于零。

最终，Center的目的是将其从父级（屏幕）接收到的紧密约束转换为其子级（Container）的松散约束。

## 无界约束

在某些情况下，盒子的约束是无界的，或者说是无限的。这意味着最大宽度或最大高度被设置为double.infinity。

一个**试图尽可能大**的盒子在给定**无界约束**时将无法正常工作，并且在调试模式下会抛出异常。

渲染盒子最终出现无界约束的最常见情况是在弹性盒子（Row或Column）内部，以及可滚动区域（如ListView和其他ScrollView子类）内部。

约束（Constraint）是 Flutter 中父组件给子组件的 “尺寸规则”，包含 minWidth/maxWidth、minHeight/maxHeight 四个值。
无界约束特指：maxWidth = double.infinity（水平方向无上限）或 maxHeight = double.infinity（垂直方向无上限）—— 简单说，就是父组件告诉子组件：“你在这个方向上想多大就多大，没有最大限制”。

“试图尽可能大的盒子”（比如没设置 width/height 的 Container、Image 等，它们的尺寸依赖父约束的 “最大边界”，默认想占满父组件给的最大空间）。
这类盒子的逻辑是：“父组件让我最大能到多少，我就多大”。但如果父组件给的是 “无限大”（无界约束），盒子就会陷入 “不知道自己该多大” 的困境 ——Flutter 无法渲染一个 “无限大” 的组件，因此在调试模式下会抛出异常（如 BoxConstraints forces an infinite width），release 模式下可能出现不可预期的布局（比如内容溢出）。

### 无界约束的 2 个最常见场景

无界约束不是 “bug”，而是某些组件的 “默认行为”，最容易出现在以下两种场景：

* 1. 弹性盒子内部（Row/Column）
  Row/Column 是 “弹性布局组件”，它们在主轴方向（Row 的主轴是水平，Column 的主轴是垂直）的约束默认是 “无界” 的 —— 因为它们的设计目的是 “容纳尽可能多的子组件”，需要允许子组件在主轴方向无限延伸（直到超出后触发溢出）。

举个例子：
如果在 Row 里放一个没设 width 的 Container（默认想占满最大宽度），Row 的水平方向是无界的，Container 就会因 “找不到最大宽度” 而报错。

```dart
Row(
  children: [
    Container(color: red), // 错误：Row水平无界，Container不知道该多宽
  ],
)
```

### 2. 可滚动区域内部（ListView/ScrollView）

可滚动组件（如 ListView）的约束规则是：滚动方向是 “无界” 的，交叉方向是 “有界” 的。

* 滚动方向（如垂直 ListView 的垂直方向）：无界（因为可以无限滚动，内容能无限延伸）；
* 交叉方向（如垂直 ListView 的水平方向）：有界（默认适应父组件的宽度，比如屏幕宽度，不能无限宽）。

但如果嵌套可滚动组件，就容易让 “交叉方向” 变成无界，触发问题。

拆解 “垂直 ListView 嵌套在水平 ListView 内部” 的场景：

* 外部水平 ListView：
  * 滚动方向是 “水平”，因此水平方向是无界的（可以无限左右滚动，没有最大宽度）；
  * 交叉方向是 “垂直”，垂直方向有界（适应父组件高度，比如屏幕高度）。
* 内部垂直 ListView：
  * 它的父组件是外部水平 ListView，因此它的 “交叉方向”（垂直 ListView 的交叉方向是 “水平”）会继承父组件的水平约束 —— 也就是无界（因为外部水平 ListView 的水平方向是无界的）；
  * 内部垂直 ListView 默认想 “占满交叉方向的最大宽度”（即水平方向），但现在水平方向是 “无限大”，它就会因 “找不到最大宽度” 而报错。

简单说：内部垂直 ListView 想知道 “自己该多宽”，但外部水平 ListView 告诉它 “你想多宽就多宽”，最终导致冲突。

## 避免无界约束

核心思路：给 “试图尽可能大的盒子”明确的最大边界，打破 “无界” 状态。

* 直接设置固定尺寸：给无界方向加 width/height（如给内部 ListView 设 width: 200）；
* 用 ConstrainedBox 限制最大尺寸：通过 maxWidth/maxHeight 强制给无界约束加 “上限”，例如：

```dart
HorizontalListView( // 外部水平ListView
  children: [
    ConstrainedBox(
      constraints: BoxConstraints(maxWidth: 300), // 强制水平最大宽度300
      child: VerticalListView(...), // 内部垂直ListView，现在知道最大宽300，正常渲染
    ),
  ],
)
```

无界约束的本质是 “父组件没给子组件明确的最大尺寸边界”，而 “想最大化的盒子” 依赖这个边界才能确定尺寸，两者冲突导致问题。最容易踩坑的场景是 “弹性盒子主轴” 和 “嵌套可滚动组件”，解决的关键就是给受影响的盒子 “手动加一个最大边界”，让它知道自己该多大。
